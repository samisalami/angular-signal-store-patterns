Where does the code
around your stores go?

How it is often organised today, and a proposal for three clear layers: domain functions, stores, and the way from store to view.

TodayProposedOptional

Today

Three kinds of code share the same places

1 · Rules live in helpers

Types sit in interface and model files. What those types can do is spread over helper files, alongside string and array utilities.

2 · Stores do three jobs

Inside withMethods you change state, write domain rules, and build objects that one particular view needs.

3 · Components wrap the store

Components inject stores and wrap store methods in event handlers. Each component with the same button writes its own wrapper.

The common cause: there is no agreed place for each kind of code. So "where does this go?" is answered per developer, per file.

Proposed

Three layers, and arrows that point one way

Domain functions

The rules about your data. Plain TypeScript, next to the type.

Store

The state, and the only place that changes it or talks to the server.

Inject functions

What several views share: who is looking, where to navigate.

1 · Domain functions

Proposed

Who calls domain functions

Queries answer a question

Post.isDraft(post), Post.isEditableBy(post, user). Safe to call from every layer.

Updates return the changed object

Post.toggleLike(post, user). Only a store calls these, because only a store can save the result.

The domain function decides what the new post is. The store decides that it is saved.

One click on ♥, traced through the layers

1

Template

The card calls like.toggleLike().

2

Inject function

Reads who is signed in and calls postsStore.toggleLike(post().id, viewer).

3

Store method + domain function

Post.toggleLike(post, viewer) returns the new post. The store saves it, tells the server, and puts the old post back if the server rejects it.

4

Signals bring it back

The state changed, so publishedPosts recomputes, the page hands the card a new post, like.isLiked recomputes, and the button re-renders.

Steps 1 and 2 change no state. Step 3 doesn't know a button exists.

3 · From store to view

Proposed

Four questions decide where code goes

#Ask in order. The first "yes" decides.Then it is a…
1Can it be written with only its arguments, importing nothing from Angular or NgRx?domain function
2Does it change state or talk to the server?store method
3Is it derived from one store's state alone, with no parameter?store computed
4Everything else: it needs a parameter, a second store, or the router.view side: in the component if one view needs it, an inject function from the second view on

Names you can check in review

Store methods never contain a view word (Viewer, Selected, ForCard). Inject functions are named after a concern, never after a component.

Lint enforces the imports

Domain files can't import Angular. Stores can't import the router. Components and inject functions can't import patchState or API services.

Keeping it consistent

Optional, if you need it

Events: when methods stop being enough

The situation it solves

Several stores or components must react to the same thing. With methods, the sender has to know and call all of them.

One rejected like, three reactions
PostsStoretakes the like back
NotificationsStoreadds a message
the like button that was clickedshows a hint

None of the three knows the others. A fourth reaction is one more on(…). Nothing that dispatches changes.

Optional@ngrx/signals/events

What it costs

More code per action, RxJS instead of async/await, and nothing for the caller to await. Methods stay the default. It's a decision per store.
